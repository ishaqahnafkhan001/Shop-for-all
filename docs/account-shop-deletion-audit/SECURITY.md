## Owner resolution: required decision and proposed safe rule

`Shop` has no canonical `ownerAccountId`. Vendor registration creates a VendorAdmin membership and a `VendorVerification` with `owner_id=Account._id`. The verification schema also supports legacy `ownerModel='User'`. Normal staff management creates only VendorStaff; it does not establish a co-owner system. [Registration](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/controllers/authController.js:463), [verification owner](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/models/VendorVerification.js:23), [staff creation](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/controllers/userController.js:142).

**Proposed:** resolve the target only from the authenticated tenant, then require all of: active Account; active User tied to that Account; active VendorAdmin membership tied to the same User/Account/shop; and an agreed authoritative owner binding. For the first supported path, the registration verification owner binding can be cross-checked, translating legacy User owners through their account relationship. Missing, duplicate, conflicting or ambiguous owner evidence must stop with an administrative reconciliation requirement. Do not create a verification record during this ownership check: the current verification service has a lazy-create path. Approval is needed before choosing whether to formalize ownership in `Shop` or a separate binding; role alone is not proof that arbitrary future administrators can erase the shop.

Before account finalization, enumerate **all** memberships, legacy Users, verification ownership references, platform/support roles and unresolved obligations for the target Account. If another relationship exists, the proposed default is to stop combined account deletion and present its scope for a separate approved decision. Deleting one shop should remain possible without erasing that Account. Never silently cascade to other shops or delete every customer/staff Account whose last membership disappeared.

## Proposed request contract

1. Authenticated preflight resolves `S` from server identity, not a request-body shop ID. Return a bounded scope summary, active obligations, account relationships, retention categories and irreversible effects. The preflight is informative, not a lock or permission grant.
2. A confirmation request supplies the current Account password, typed shop/subdomain confirmation, a client operation ID and the reviewed scope/policy version. Verify the password with the existing bcrypt hash comparison. A separate confirmation endpoint is optional; the smallest safe first version verifies the password directly in the acceptance request. Do not persist or log it.
3. Recheck ownership, relationship scope, obligations and current versions in the acceptance transaction. Bind the idempotency key to account, shop, target type and normalized request scope. Same key/scope replays the same request; a different scope conflicts. Enforce only one active deletion per shop independently of the client key.
4. Commit a durable request plus shop fence and job/audit intent atomically. Return 202 with request ID and exact accepted state, not a deletion-success message. A lost response must not start another cleanup.
5. Invalidate scoped sessions and reject normal shop writes. If full Account deletion is authorized, all its memberships/session artifacts require explicit handling; another shop's staff/customers remain untouched.
6. Normal status access must be authenticated to the requesting Account or an explicitly authorized platform operator. To resolve a lost acceptance response after immediate session revocation or Account removal, the authenticated preflight should also issue a **separate, short-lived, purpose-bound read-only receipt capability before submission**. Reuse the existing signed/HMAC token pattern, with a distinct purpose, account/shop/operation binding, random nonce, expiry and a persisted grant hash in the accepted request. It can return only minimal operation state/error codes; it must not authorize deletion, cancellation, retained data access or general login. Send it in a protected header, never a URL/query, and rate-limit the receipt route. A request ID alone is not a bearer secret. Once this receipt expires, use a legitimate remaining Account membership or platform support, not a revived deleted account. Receipt lifetime/storage/recovery UX need product/security approval. Do not weaken normal session revocation to support polling.

Proposed error semantics: 401 invalid/expired authentication; 403 staff/non-owner; 404 inaccessible tenant resource; 409 conflicting operation, changed scope or active obligation; 400 invalid confirmation; 429 rate limit; 202 accepted/replayed in-progress request. Final status names and customer-facing wording require product review.

CSRF already protects unsafe cookie-authenticated requests with signed double-submit tokens; the deletion route must not enter its exclusions. Reuse the auth rate-limit infrastructure and add account/shop/IP attempt limits with enumeration-safe errors. [CSRF](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/middlewares/csrf.js:55), [step-up limiter](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/routes/authRoutes.js:75). Infrastructure-wide rate-limit consistency across multiple instances remains unknown.

## Attack cases and required proof

| Scenario | Required outcome and test |
|---|---|
| Employee has every settings permission | Denied: VendorStaff cannot gain owner deletion authority through permission flags. API and browser tests. |
| A submits B's shop or request ID | No B data or scope leakage; server derives S and checks all references. Two-tenant HTTP/DB tests. |
| Old stolen session; current password unknown | Confirmation denied; failed attempts rate-limited; password never enters audit/job data. |
| Attacker replays checkout/reset/order OTP | Rejected as wrong purpose and scope. Unit/service tests. |
| Wrong legacy owner model or another VendorAdmin | Fail closed pending owner reconciliation; do not guess a single owner. |
| Same request concurrently submitted twice | One active request, job and cutoff; matching retries replay; changed payload conflicts. Transaction integration tests. |
| Account has another owner/staff/customer/platform role | No automatic global Account deletion; other memberships and credentials preserved. |
| A request already passed middleware when shutdown commits | Its database write conflicts with the deletion fence or its admitted operation is drained before purge. Controlled interleaving tests. |
| Worker cancelled while an HTTP provider call is in flight | No claim that cancellation undoes the call; reconcile provider result before declaring cleanup complete. |
| Deleted Account still has a legacy User | Login/reset must not recreate the Account through legacy migration fallback. [Login fallback](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/controllers/authController.js:764), [reset fallback](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/services/passwordResetService.js:103). |
| Recovery code sets isActive/approvalStatus | Deletion fence takes precedence over verification/billing recovery and Super Admin activation. |
| Backup or audit outbox resurrects information | Replay deletion ledger before traffic and before outbox/worker processing; anonymization applies to the outbox as well as materialized logs. |

Do not log passwords, full media manifests, NID, customer contact details or unrestricted provider payloads. The existing general audit logger is best effort; use the critical transaction/outbox pattern for acceptance and milestones. Redaction is not erasure: stdout, free text and retained audit snapshots need their own approved lifecycle. [Critical outbox](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/services/platformAuditOutboxService.js:119), [logger](/Users/user/Downloads/Shop-for-all/ecommerce-backend/backend/services/logger.js:23).
