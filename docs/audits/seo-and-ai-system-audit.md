# Shop for All SEO and AI System Audit

**Audit date:** 2026-08-10
**Scope:** Current repository implementation of storefront SEO and first-party AI used by Product creation, Catalog Tools, Growth Center, plus the Homepage SEO AI that is part of the SEO workflow.
**Method:** Static repository tracing from admin UI entry points through API routes, middleware, controllers, services, models, shared packages, storefront metadata/JSON-LD, workers, tests, and configuration references. No production API, merchant account, external AI provider, DNS, or Search Console operation was performed.
**Change policy:** This report is the only artifact created. No application code, prompt, schema, route, or UI behavior was changed.

## 1. Executive Summary

Shop for All has a materially better SEO foundation than a typical early-stage multi-tenant storefront. Homepage SEO has a shared contract in `packages/storefront-theme/homepage-seo.cjs`, published custom-domain canonicals preserve the exact verified host, metadata is generated by Next.js server routes, and Homepage SEO uses a proper draft/revision/publish workflow. Product and collection pages generate server metadata, canonical links, breadcrumbs, and structured data. Tenant-scoped public queries exclude inactive, deleted, and unpublished products.

The current SEO system is not yet a production-quality 10/10 system. The largest correctness gaps are incomplete sitemap coverage and scale, soft-404 behavior for missing shops/products, no redirect history after product slug changes, no dedicated category SEO fields, limited Product structured data, and rating aggregates that have no moderation/eligibility state. Homepage SEO is also unnecessarily coupled to the broader `storeBuilder` entitlement even though it has a dedicated dashboard workspace.

Four current first-party Gemini workflows were confirmed:

1. Image-aware Product content suggestions.
2. Collection content/SEO suggestions in Catalog Tools.
3. Growth Center ad-planning copy and audience suggestions.
4. Homepage SEO alternatives.

A fifth, legacy Product description endpoint remains mounted but has no current admin caller. All generation is synchronous; no AI generation worker exists. Product AI is the most mature: it has image controls, an output schema, timeout, bounded context, one quality retry, usage reservation, safe errors, a preview, and explicit vendor application. Homepage SEO AI is also well controlled. Catalog and Growth AI are less consistent: neither uses the canonical AI usage reservation, and Growth has neither a dedicated rate limiter nor a way to tell users whether Gemini or deterministic fallback produced the answer. Growth fallback text can claim Cash on Delivery, easy/fast delivery, or limited stock without confirming those facts.

**Current evidence-based scores:** SEO **7.7/10**; AI system **7.1/10** overall, with Product AI at **8.4/10**, Homepage SEO AI at **8.2/10**, Catalog collection AI at **7.6/10**, Growth ad AI at **6.2/10**, and the legacy description prompt at **3.8/10**.

## 3. SEO Architecture and Data-Flow Overview

### Ownership and source of truth

Storefront rendering and final Next.js metadata are owned by `ecommerce-storefront`. The canonical homepage SEO rules are shared through `@scaleup/storefront-theme`, implemented in `packages/storefront-theme/homepage-seo.cjs`. The backend and admin both consume that shared resolver. Product/category/collection metadata helpers remain in `ecommerce-storefront/src/lib/seo.js`, so SEO is centralized for the homepage but not for every page type.

Persisted SEO data is split by resource:

- Homepage: `Shop.theme.seo` plus `Shop.searchAliases`.
- Homepage draft: `StoreBuilderDraft.theme.seo` plus `StoreBuilderDraft.searchAliases`.
- Published history: `StoreBuilderRevision.theme` and `searchAliases`.
- Product: `Product.seo.title`, `Product.seo.description`, `Product.slug`, and `Product.imageAltText`.
- Collection: `Collection.seo.title`, `Collection.seo.description`, and `Collection.slug`.
- Category: `Category` stores name and cover-image metadata, but **no dedicated SEO title/description fields**.

### Confirmed Homepage SEO flow

```text
Vendor input in HomepageSeoPage
  -> useHomepageSeo local draft
  -> PUT /api/store-builder/admin/seo/draft
  -> authentication + role + permission + feature + suspension guards
  -> shared theme sanitizer/normalizer
  -> StoreBuilderDraft with basedOnRevision
  -> POST /api/store-builder/admin/seo/publish after vendor action
  -> transaction/revision conflict check + Shop.theme/searchAliases update
  -> StoreBuilderRevision + audit + storefront cache invalidation
  -> public storefront bootstrap/info
  -> shared resolveHomepageSeo
  -> Next.js generateMetadata + WebSite/OnlineStore JSON-LD
  -> server-rendered head/script output
```

### Draft, publishing, conflicts, and rollback

- `useHomepageSeo` maintains separate published and local draft values, autosaves after 1.2 seconds, warns on browser unload, and preserves local edits during revision conflict recovery.
- `StoreBuilderDraft.basedOnRevision` and `Shop.themeRevision` protect against stale publishing.
- `publishStoreBuilder` uses a revision filter and reports `THEME_CONFLICT` on concurrent publish.
- `StoreBuilderRevision` keeps published snapshots and a `changeScope`; rollback support is part of the shared Store Builder service.
- SEO-only draft deletion rebases the draft rather than deleting unrelated Store Builder work.
- Publish updates local state from the server response and then reloads bootstrap. This is compatible with current full-response behavior, although the post-publish reload is unnecessary work and would be risky if a deployment served stale responses.

### Tenant isolation

- Admin SEO derives the shop from authenticated tenant context; clients do not supply an authoritative shop ID.
- Product, collection, category, and Growth queries include `shop_id: req.tenantId`.
- Store search selects only approved, active, verified shops and uses normalized tenant-owned names/aliases.
- Public storefront host forwarding is signed with `STOREFRONT_PROXY_SECRET` outside development.
- Verified custom-domain use requires stored domain, ownership verification, and routing/manual routing verification. Arbitrary request hosts do not become canonicals.

The Homepage SEO admin has dedicated tabs for Search Appearance, Search Identity, Social Sharing, Indexing, AI Assistant, and SEO Health. It is no longer only an embedded Store Builder panel. However, all SEO routes still require both `requireShopFeature('storeBuilder')` and `requireShopFeature('homepageSeo')`, plus `storeBuilder` permission. This makes `homepageSeo` incapable of operating as an independent entitlement.

The client preview resolver receives less context than the backend/live resolver: it does not provide current hero copy, catalog summary, social profiles, or contact data. The health score includes backend counts but the actual draft preview can differ from live generated fallbacks. Compatibility mode also treats `customDomain.status === 'Verified'` more loosely than the shared resolver's ownership/routing checks.

### 4.2 Product SEO

- Public product detail lookup is tenant-scoped and accepts slug or ObjectId. ObjectId URLs redirect to the current slug.
- Only active, non-deleted, `Published` products are returned by public product queries.
- Product title priority is `product.seo.title` then product title.
- Product description priority is `product.seo.description`, short description, description, then a generated safe fallback.
- Product canonical is `/products/:slug` on the exact canonical tenant origin.
- Product images prefer cover/gallery and `imageAltText`; image helpers tolerate null products.
- Product JSON-LD includes Product name, description, image array, SKU, brand, Offer price/currency/availability/URL, and AggregateRating when both denormalized values are positive.
- Breadcrumb JSON-LD links store -> category -> product.
- Product Add/Edit exposes SEO title/description, URL slug guidance, alt text, health score, and snippet preview.

Risks and gaps:

1. A missing product returns noindex metadata but the page does not call `notFound()`. `ProductDetails` receives `initialProduct=null`, so the HTTP response can remain `200` and become a soft 404.
2. Changing a slug has no persisted old-slug/redirect history. Only ObjectId-to-current-slug redirects exist; old shared slug URLs can become 404s.
3. Product JSON-LD lacks `itemCondition`, `priceValidUntil`, seller, shipping details, and merchant return policy.
4. `Review` has no publication/moderation/eligibility status. Every stored review contributes to `averageRating`/`numReviews`. Therefore the audit cannot certify that schema ratings come only from eligible/published reviews.
5. Rating recalculation is attached to `save` and document `remove`. No review deletion path was found, but future query-based deletion could bypass recalculation unless explicitly handled.
6. The public serializer correctly excludes buying price and inventory internals, but structured-data tests are mainly source assertions rather than rendered-schema validation against varied persisted documents.
7. Bengali product names are preserved by Unicode-aware cleaning and no production code fabricates an English translation. There is no separate bilingual title/translation model; bilingual support is genuine vendor-entered text only.

### 4.3 Category SEO

- Category routes use tenant-scoped category metadata and tenant-scoped public Product queries.
- Category page metadata is generated from the category name and shop identity.
- Canonical is `/categories/:slug` with query parameters removed.
- Category pages render a semantic `h1`, cover alt text, breadcrumbs, and current-page ItemList JSON-LD.
- Missing categories call `notFound()`.
- Category product counts and covers are available.

The `Category` schema has no SEO title, SEO description, redirect history, or explicit localized name fields. Category metadata is generated, not vendor-editable. Category URLs are also absent from the XML sitemap. Filters, sorting, price, sale, stock, and pagination use query parameters but canonicalize to the clean category URL. That limits duplicate content but means all pages in a paginated category share one canonical; direct Product sitemap links partly compensate, but category discovery and pagination signals are incomplete.

### 4.4 Collection SEO

- Collections persist title, description, slug, image, product IDs, active state, and SEO title/description.
- Public collection queries require an active collection and return public/published products.
- Metadata uses saved collection SEO fields with title/description fallbacks.
- Canonical is `/collections/:slug`; page outputs Breadcrumb and ItemList JSON-LD.
- Empty collections are omitted from the sitemap.
- Catalog AI can suggest collection copy and SEO, but only a vendor apply action mutates the local form and a separate save persists it.

There is no collection slug redirect history. ItemList reflects only the fetched products, not a complete multi-page collection.

### 4.5 Robots and sitemaps

Tenant `robots.txt`:

- Uses the same canonical origin helper as metadata.
- Points to `{canonicalOrigin}/sitemap.xml`.
- Disallows cart, checkout, account/auth, tracking, search, API, dashboard/admin, and preview prefixes.
- On backend failure returns `Disallow: /` rather than accidentally permitting a broken storefront.

Tenant sitemap:

- Contains homepage, policy overview, published Product slug URLs, nonempty active Collections, and configured policy pages.
- Uses exact canonical-domain helpers and public tenant APIs.
- Returns an empty sitemap when the shop is not search-visible.

Gaps:

- It fetches only page 1 with `limit: 2500`; there is no sitemap index or pagination loop, so Product 2501+ is omitted.
- Category URLs are not included.
- Sitemap/backend failures return an empty `200` response, which hides operational failure from monitoring and search engines.
- No image sitemap, video sitemap, or hreflang sitemap exists.
- No explicit duplicate URL de-duplication occurs before XML assembly.

### 4.6 URL normalization, status, and duplicates

- Verified-domain canonical selection intentionally preserves www or apex exactly as saved and verified. The application does not force or remove www.
- Root canonical includes `/`; inner canonicals do not include a trailing slash. No explicit Next `trailingSlash` rule was found, so platform behavior supplies the redirect policy.
- Legacy homepage `?category=` redirects to `/categories/:slug`.
- Other unknown homepage query parameters are not stripped by an app redirect, although canonical metadata points to `/`.
- Filter/query pages canonicalize to their clean category/collection origin; no alternate metadata exists per page.
- Category and Collection misses use real 404s. Product misses and missing-store homepage responses can be soft 404s because they render an unavailable state without `notFound()`.
- No old-slug redirect store/service was found for Product, Collection, or Category.

### 4.7 Images, headings, links, and performance

Strengths:

- Hero and cards use Cloudinary transformation helpers, responsive `srcSet`/`sizes`, dimensions, lazy loading for non-hero images, and high fetch priority for the first hero image.
- Main pages have semantic `h1`; homepage emits a screen-reader `h1` when the visible hero is hidden.
- Product/category/collection cards use clean internal links and breadcrumb links.
- Public metadata and JSON-LD are server-rendered.

Risks:

- The shared storefront renderer is a broad client-component tree. HTML can still be server-rendered, but hydration and route JavaScript are larger than a server-component-first storefront.
- Raw `<img>` is used intentionally instead of Next Image, so Next's built-in optimizer and image preload integration are not used.
- Several decorative/brand-story/banner images have `alt=""`; appropriate for decoration, but the current model cannot provide section-specific meaningful alt text when the image carries content.
- Homepage metadata and page data can trigger separate backend bootstrap calls. Custom domains and `fresh:true` use `no-store`; this improves freshness but increases latency/backend work.
- Public fetch revalidation is 30-60 seconds on platform subdomains. Store Builder publishing performs cache invalidation, but Next data cache invalidation is not visibly tag-driven; stale metadata may remain for a bounded revalidation period.
- `firstHeroImage` in storefront SEO helpers refers to legacy `hero.slides`, while the current contract uses `hero.bannerSlides`. Product/inner-page social fallback can miss a valid banner image if no logo/social image exists.

### 4.8 Search aliases and internal storefront search

Search aliases are both internal-search signals and structured-data alternate names; they are not meta keywords.

- Maximum eight stored aliases, maximum 60 characters each.
- Unicode NFKC/lowercase normalization preserves Bengali letters.
- Duplicate aliases and the exact official name are removed.
- URLs, emails, phone numbers, excessive punctuation, keyword phrases over six words, and aliases without a canonical token shared with the official name are rejected.
- Spelling groups cover jewellery/jewelry/jewelery/jewellry, colour/color, personalised/personalized, and centre/center.
- `searchAliasesNormalized` and `searchNameNormalized` have tenant-safe indexes.
- Marketplace store search ranks exact official name above exact aliases, prefix matches, spelling variants, and bounded fuzzy matches.
- Published aliases are included as up to five `alternateName` values in WebSite JSON-LD.
- Draft aliases do not affect public search until publish.

Audit scenario: for official name `ADI Jewellery`, inputs such as `Adi jewelry`, `ADI Jewelry`, `ADI Jewelery`, and `Adi jewellry` normalize as genuine variants and are covered by tests. The exact official spelling is intentionally removed as a redundant alias. If a shop's official `Shop.shopName` is only `ADI` or another name that does not share a canonical token, those aliases correctly fail. The admin should expose that authoritative official-name dependency more clearly.

### 4.9 SEO security

- Shared cleaners strip script/style tags, HTML, control characters, and bound lengths.
- Theme payloads allowlist top-level fields, reject Mongo-style keys, validate hex colors, and neutralize `javascript:`, `vbscript:`, unsafe `data:`, protocol-relative, and invalid navigation/media URLs.
- Google verification input is reduced to a safe content token.
- JSON-LD is serialized with `<` escaped as `\u003c`.
- Public Product serializers allowlist customer-safe price and content fields and exclude buying price, inventory internals, supplier/admin data, and private shop data.
- AI alternatives cannot publish themselves; they only update local draft and preserve accepted-option provenance.
- Unknown theme fields are dropped safely.

No cross-tenant SEO read/write path was found in the traced routes. The main entitlement concern is coupling, not tenant leakage.

## 5. SEO Strengths

1. Exact verified-domain canonical behavior is deliberate, shared, and tested for www/apex/platform fallback.
2. Homepage SEO has real draft, revision, conflict, publish, audit, and rollback architecture rather than direct Shop mutation.
3. The shared homepage resolver provides deterministic fallbacks and field provenance (`manual`, `ai`, `generated`, `fallback`, `missing`).
4. Next.js server metadata and server-inserted JSON-LD make core search data available without waiting for browser JavaScript.
5. Tenant isolation and public serializers are consistently backend-authoritative.
6. AI suggestions require vendor review and explicit publish.
7. Private commerce/account routes are noindexed and disallowed.
8. Public Product queries exclude deleted, inactive, and unpublished products.
9. Alias handling is Unicode-aware, bounded, indexed, and protects the official brand identity.
10. Theme normalization preserves old SEO fields (`keywords`) while synchronizing the newer `topics` contract.

## 6. SEO Problems and Missing Capabilities

### Critical/high correctness issues

1. **Soft 404s:** missing Product and missing-store homepage flows can return `200` unavailable screens.
2. **Sitemap truncation:** only the first 2,500 Products are fetched; no sitemap index exists.
3. **Category omission:** Categories are first-class canonical pages but absent from the sitemap and have no editable SEO model.
4. **Slug continuity:** no redirect history exists after slug edits.
5. **Rating eligibility:** Review has no approved/published state, so schema cannot distinguish eligible public reviews.

### Architectural/quality gaps

6. Homepage SEO requires Store Builder entitlement/permission as well as Homepage SEO.
7. Homepage indexability is shared and environment-aware; Product/Collection/Category use a simpler `isShopSearchVisible` path, creating policy duplication.
8. Client draft preview lacks enough context to exactly match backend/live generated metadata.
9. Product structured data is only a baseline Offer and lacks shipping/returns/seller fields.
10. Inner-page social-image fallback reads legacy `hero.slides`, not the canonical `bannerSlides` field.
11. No sitemap health telemetry; failure becomes a valid empty `200` document.
12. No hreflang or language-alternate URLs. This is acceptable while there are no separate translated URLs, but international SEO is limited.
13. No category/collection/product field provenance or revision history outside the Store Builder homepage workflow.
14. No automated rendered-page crawl test validates HTTP status, head tags, JSON-LD, robots, sitemap, and canonical consistency together.

## 9. AI Architecture and Data-Flow Overview

All confirmed first-party generation uses `@google/generative-ai` and defaults to `gemini-2.5-flash`, with optional `GEMINI_MODEL`. No OpenAI/Anthropic runtime call and no AI worker was found.

### Product AI

```text
Add/Edit Product -> ProductAiAssistant builds multipart FormData
-> POST /api/admin/products/ai/content-suggest
-> auth/role/products permission/aiProductCreation/billing/verification/rate limit/upload checks
-> reserve weekly AI usage atomically
-> build bounded safe context + optional memory image/trusted Cloudinary fetch
-> Gemini JSON-schema request (synchronous)
-> parse/sanitize/quality check -> one strict retry or evidence-based fallback
-> complete/release usage reservation
-> preview modal -> vendor applies selected fields -> normal Product save
```

### Catalog collection AI

```text
Catalog Tools collection form -> selected Product IDs/title/context
-> POST /api/admin/collections/ai/suggest
-> auth/role/catalogTools permission/bulkProductTools feature/collectionsAi permission/verification/rate limit
-> tenant-scoped Product lookup (up to 30, including draft/private seller catalog content)
-> Gemini JSON-schema request (synchronous)
-> normalize or deterministic parse fallback
-> preview -> vendor applies fields -> separate collection save
```

### Growth Center AI

```text
Growth Center Product + range/language/campaign selection
-> POST /api/admin/growth/generate-ad-copy
-> auth/role/growthCenter permission + growthCenter and aiAdGenerator features
-> tenant Product + application-calculated analytics + aggregate cities/search terms
-> Gemini JSON request (synchronous)
-> sanitize or silent deterministic fallback
-> UI planning card for vendor to copy; nothing is published/saved as an ad
```

### Homepage SEO AI

```text
Homepage SEO AI Assistant -> current draft preferences
-> POST /api/store-builder/admin/seo/ai-suggest
-> Store Builder/SEO permission and feature guards + verification + rate limit
-> tenant-safe shop/catalog context
-> Gemini JSON request (synchronous)
-> normalize three alternatives or fallback
-> preview/apply to local draft -> explicit publish required
```

## 11. Product-Creation Prompt Report

### Trigger and endpoint

- Trigger: main “Generate better content with AI” or section buttons for SEO, description, selling points, specifications, extra notes, and image alt.
- Frontend: `ecommerce-admin/src/components/products/ProductAiAssistant.jsx`.
- Endpoint/controller: `/api/admin/products/ai/content-suggest` -> `productController.generateProductContent`.
- Execution: synchronous request; optional first image stays memory-only and is not uploaded by AI.
- Persistence: none until vendor applies suggestions and submits Product form.

### Data sent

The form sends title, category, tags, selling price, visible variants, existing description/SEO/features/specifications/customer-facing comments, language hint, requested sections, and either the first local `image` file or existing `imageUrl`. Backend parsing bounds multipart JSON/string fields. The prompt explicitly excludes buying price, cost, supplier, private customer, and internal admin fields.

Local images are JPEG/PNG/WebP, maximum 5 MB. Existing URLs must be HTTPS and on Cloudinary or `TRUSTED_PRODUCT_IMAGE_HOSTS`; redirects are rejected, response MIME/size are checked, and timeout is five seconds. `usedImage` is true only when a valid image part reaches Gemini.

### Model and settings

- Provider: Google Gemini SDK.
- Model: `GEMINI_MODEL` or `gemini-2.5-flash`.
- Temperature 0.25; top-p 0.8.
- Max output: `GEMINI_PRODUCT_AI_MAX_OUTPUT_TOKENS` or 2,400.
- Response MIME: `application/json`; explicit Gemini response schema.
- Timeout: text default 30s, image default 45s; bounded to 15-60s (image minimum 30s).
- Safety settings: no explicit SDK safety-settings override; provider defaults apply.
- Retry: one strict retry when parse fails or requested selling points are too weak/few.

### Expected output and validation

Output contains SEO title/description, description, image analysis, “why buy” points, specifications, extra notes, image alt, and confidence notes. The cleaner strips HTML/control characters, bounds all fields, normalizes arrays/objects, removes unsafe claims, and maps `whyBuy` to the public `sellingPoints` shape. If the provider output cannot be used, an evidence-based fallback is generated only when enough seller evidence exists; otherwise the request returns an insufficient-context message.

### Overwrite and approval behavior

- Suggestions appear in a modal.
- Existing values are not replaced until the vendor clicks a section apply/replace button or Apply all.
- Selling points support append and replace.
- Applying changes the local form and marks it for normal review/save.
- No AI result auto-publishes.

### Product AI assessment

Strong grounding language, image evidence separation, field-level approval, output schema, timeout cleanup, usage reservation, and private-price exclusions are present. Remaining gaps are no formal prompt version/model version in generated provenance, no per-generation cost/token record, no idempotency key (a retry can consume another generation), and no explicit instruction that merchant context is untrusted prompt data. The prompt says “trusted product text,” which is inappropriate for prompt-injection defense even though output sanitization limits downstream damage.

### 14.1 Product content prompt (`productContentAiService.buildPrompt`)

```text
You are an ecommerce product content assistant for Bangladeshi small online sellers.
Return ONLY valid JSON. Do not include markdown, comments, or explanations.
{STRICT_RETRY_LINE_OR_EMPTY}

{
  "seoTitle": "string",
  "seoDescription": "string",
  "description": "string",
  "imageAnalysis": { "summary": "string", "productType": "string", "visibleAttributes": ["string"], "uncertainAttributes": ["string"], "confidence": "low|medium|high" },
  "whyBuy": [{ "point": "string", "reason": "string", "visualEvidence": "string", "confidence": "low|medium|high" }],
  "specifications": [{ "label": "string", "value": "string" }],
  "extraNotes": ["string"],
  "imageAlt": "string",
  "confidenceNotes": ["string"]
}

Rules:
{IMAGE_PRESENT_OR_TEXT_ONLY_RULE}
- Combine image evidence with product title, category, tags, variants, specifications, and existing product description.
- In imageAnalysis, separate observed image details from uncertain or unsupported details.
- Do not claim uncertain materials, dimensions, brands, medical benefits, purity, waterproofing, warranty, certifications, authenticity, or guarantees.
- Do not say #1, best in Bangladesh, guaranteed, or use keyword stuffing.
- Preserve Bangla, English, or mixed tone based on the product title and existing content.
- SEO title target: 50-70 characters.
- SEO description target: 120-160 characters.
- Description target: 60-110 words, concise and product-specific.
- whyBuy: write 3-5 high-quality point/reason/visualEvidence/confidence objects.
- Each point must be 1-5 words, maximum 60 characters, specific, and easy to scan.
- Each reason must be 10-28 words, maximum 220 characters, evidence-based, customer-focused, and honest.
- Each visualEvidence must state what was observed in the image or which trusted product data supports the claim.
- Selling point pattern: point -> evidence from image/product data -> customer value.
- Do not produce vague headings like "Clear details", "Image confidence", "Choice options", "Customer choice", "Product quality", "Premium quality", "Best product", "Great product", "Good design", "Stylish product", "Perfect choice", "Must buy", or "Value for money".
- Do not write generic reasons like "helps customers understand", "shown clearly before ordering", "gives customers confidence", "suitable for shoppers looking for this product", "matches customer needs", "is a good option", or "helps shoppers decide".
- For jewellery, focus on visible design, pattern, styling versatility, occasion suitability, and gifting only when reasonable. Do not invent metal, purity, stones, or weight.
- For clothing, focus on visible cut, styling, color coordination, fit options, and occasion suitability. Do not invent fabric or durability unless supplied.
- For electronics, focus on visible controls and documented features. Do not invent battery, chipset, waterproof rating, or benchmarks.
- For beauty or healthcare products, do not generate medical or treatment claims.
- Specifications: 4-8 safe rows. Do not invent exact material, dimensions, or weight unless provided.
- Extra notes: 2-4 practical shopper notes, not internal admin notes.
- Image alt: concise product image description.
- Never include buying price, cost price, supplier info, private customer data, or internal admin data.

Image available: {yes|no}
Safe product context: {BOUNDED_JSON_CONTEXT}
```

```text

```

Image rule is one of:

```text
- Treat the product image as a primary source. Carefully inspect visible product type, shape, design, pattern, color/finish, decorative elements, form factor, style, and use context.
```

```text

```

### Quotas, rate limits, and cost

- Product modern has 30 requests/15 minutes in production.
- Collection has 30 requests/15 minutes but no weekly usage reservation.
- Homepage SEO has 12 requests/15 minutes but no plan-usage reservation.

### Prompt injection and output safety

- Homepage SEO explicitly encloses untrusted store data and tells the model not to follow it.
- Product, Collection, and Growth call their payload “safe” or “trusted” but do not separate merchant text from instructions. Stored Product descriptions/tags can contain prompt injection text.
- Output sanitizers substantially reduce executable-content risk, but injection can still alter benign-looking copy/targeting.
- Product and Collection use SDK response schemas. Homepage SEO and Growth request JSON MIME but do not configure response schema.
- JSON-LD and theme rendering independently sanitize/escape accepted output, providing defense in depth.

### Privacy

- No AI key is exposed to browser code. `GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_TIMEOUT_MS`, `GEMINI_PRODUCT_AI_MAX_OUTPUT_TOKENS`, and `TRUSTED_PRODUCT_IMAGE_HOSTS` are backend variables.
- Product excludes buying/cost/supplier/customer/admin data.
- Collection sends selected seller catalog content only; it may include unpublished Products.
- Growth sends aggregated metrics, cities, and search terms, not direct identifiers. A minimum cohort/aggregation threshold is missing.
- Homepage SEO sends public/seller storefront identity and catalog summary only. Sending subdomain is unnecessary but not secret.
- Logs contain request/shop/provider diagnostics, not prompt bodies or raw model responses in traced modern services. Legacy errors log provider error objects, which should be reviewed for SDK payload leakage.

### Reliability and failure behavior

- Product: bounded timeouts, cleared timer, one quality retry, provider error classification, safe user messages, usage release on failure, optional evidence fallback.
- Collection: timeout and safe parse fallback; provider failure is user-visible. Timer is not cleared.
- Homepage SEO: timeout timer is cleared; malformed response uses fallback. The returned `fallback` indicator can be wrong on parse fallback.
- Growth: provider/missing-key/parse failures silently use fallback. Timer is not cleared. Frontend cannot identify source or degraded quality.
- Legacy Product endpoint: no explicit timeout or safe missing-key path and returns generic HTTP 500 for expected provider failures.
- All calls are synchronous. No retry queue, circuit breaker, provider fallback model, or concurrency coalescing exists.

### Persistence and auditability

- Product and Collection suggestions are transient until vendor applies and saves.
- Growth output is transient and not cached/saved.
- Homepage SEO stores accepted alternative provenance in `theme.seo.aiSuggestion` after publish.
- Product usage events are emitted, but no common AI generation audit records prompt version, model, fallback, latency, or accepted fields across all four features.

## 19. Recommended Implementation Roadmap

### Phase 0: Immediate safety and correctness

#### 0.1 Ground all Growth claims

- **Goal:** No AI/fallback output states COD, shipping speed/coverage, stock urgency, warranty, discount, or returns unless supplied by authoritative context.
- **Reason:** Current deterministic fallback fabricates those claims.
- **Affected area:** `adInsightAIService.js`, Growth controller context, Growth UI.
- **Dependencies:** Public-safe shop shipping/payment/stock facts or omission rules.
- **Backward compatibility:** Keep response fields; add `source`, `fallback`, `limitations`, and evidence metadata additively.
- **Tests:** Missing/configured COD, shipping, stock, Bangla/Banglish fallback, provider malformed response.
- **Definition of done:** Every factual phrase maps to an explicit input; fallback is visibly labeled.

#### 0.2 Enforce one AI entitlement/quota policy

- **Goal:** Product, Collection, Growth, and Homepage SEO share authoritative feature/usage/rate controls.
- **Reason:** Current cost access differs by route.
